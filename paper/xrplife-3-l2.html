A dedicated ledger for neuromodulation: XRPLife L2, a zero-reserve rippled network anchored to the public XRP Ledger

Julien Cugny

Independent researcher · github.com/LeDenti · 4 November 2026 · technical note, version 1

Abstract. The modulatory layer of a ledger-resident C. elegans (serotonin and PDF-1 as neuron-issued currencies, receptors as trust lines) runs at the pace of the public XRPL testnet, four seconds per ledger, on a ledger that is reset from time to time and that charges a reserve per object. We describe a dedicated network running the same software (rippled 3.3.0), with its own network identifier (7302), zero account and owner reserve, 10-drop fees, all 47 votable amendments of the current release enabled at genesis, and no connection to the public network. Neurons keep the keys and addresses they have on the testnet, so one entity carries its layers on two ledgers; serotonin issued by a neuron of one animal can be received by a neuron of another. The state of the dedicated ledger is periodically anchored on the public testnet by an AccountSet memo of the organism: the settlement of the plastic layer on the immutable one, which the project calls sleep. We report the configuration, the bootstrapping procedure, seven pitfalls measured on a two-node test bench (validator and follower in Docker), the neutralisation of the public genesis account, a burst of 200 payments validated 200/200, the first anchor, and the trust model: a ledger is worth the published list of those who hold it, and this one currently has one.

1. Why a second ledger

Three properties of the public testnet work against the modulatory layer: a ledger every 3–4 s, where a mood should be set and cleared in seconds; a reserve of 0.2 XRP per trust line, which made 994 receptor lines cost 239.8 XRP; and periodic resets, which kill the organism. The layered model of the project assigns each biological time scale to a layer (genome and wired structure on the immutable L1; plastic states on an L2 anchored to it; electrical activity off-chain), and asks that each added layer state its added trust assumption. A dedicated rippled network is the smallest L2 that keeps the object-by-object correspondence of the L1: the same accounts, trust lines, payments and memos, read with the same tools.

3. Bootstrapping

  1. Generate validator keys with validator-keys create_keys and a token with create_token; only the public key (nHB…) leaves the machine. First validator: nHBdG1EX5awA6ZXr3z3hN1YbXdE6PGm45ZLoJKCcfM7ZTnJs3XfN.
  2. Start the validator in network mode with --start: a fresh genesis with the listed amendments, reserve 0. (Standalone mode, -a, does not persist its ledgers in a form that --load recovers; see §5.)
  3. Start a follower that knows the validator ([ips_fixed]). Consensus begins only once the validator has at least one peer.
  4. Neutralise the genesis account, whose passphrase is public: pay its balance to a project treasury (r3eBiYU5S8EQtfehtGTywzc6bd86kjmGpt, 99,999,999,900 units), set its regular key to the black-hole address rrrrrrrrrrrrrrrrrrrrBZbvji, disable its master key (three tesSUCCESS).
  5. Later restarts use --load; stop with the admin stop command, never by killing the process.

5. Seven pitfalls, each measured

  1. Standalone ledgers are not loadable. Ledgers accepted in standalone mode (-a, ledger_accept) were not found by --load ("Ledger not found"), even after a clean stop. Creating the genesis directly in network mode with --start works and persists.
  2. Amendments must be enabled at genesis. Voting them afterwards requires the two-week majority period even in standalone mode (44 votes cast, 0 activated at the next flag ledger). The [amendments] section expects <id> <name>; a bare name aborts the start ("Invalid entry 'AMM'").
  3. An empty [ips] section does not isolate. The node connected to ten mainnet peers (version 3.4.1, ledgers above 108 million). An inert entry stops the bootstrap; the peer cache must be purged.
  4. A validator with no peer closes no ledger. State disconnected, ledger index frozen for a minute, consensus resumed as soon as the follower connected. A one-node network needs two processes.
  5. Kill versus stop. docker rm -f lost the last ledgers; the admin stop command followed by a clean exit did not.
  6. Names in [ips_fixed] must resolve. Container names are not DNS names on a Docker network unless given as aliases.
  7. The token file is not a config fragment. validator-keys create_token prints prose before the [validator_token] block; pasted whole after [amendments], the prose was parsed as an amendment entry.

6. Trust model

A validator on this network is a partner running one process on one server; it holds no funds and signs ledgers, not payments. Agreement among 80 % of the trusted list advances the ledger and admits new validators. With one validator the chain is a signed database run by its author; with five it is a small network; with twenty it is a public good. The repository publishes the list and says which of the three it is. There is no token to buy, sell or earn: the native asset pays fees and sits in the treasury; the modulators are non-transferable IOUs of neurons. Anchoring hashes on the public ledger does not transfer value and needs no bridge; it only makes the L2 history as hard to rewrite as the L1 history after the fact.

7. What remains

The bench runs on a laptop. The first real validator needs an x86 server with 2 cores and 4 GB, separate from any machine holding exchange keys; the second validator is the hard one to recruit, and the invitation page (l2/INVITATION.md) states what is asked and what is given. The anchoring will run on a schedule. Then the modulatory experiments of the companion paper can be repeated at the L2 pace, with serotonin crossing from one animal to another, which the public testnet already permits but slowly.
